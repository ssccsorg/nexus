# 160: synTagma Integration -- CoordSpaceN + HashMap dual storage, axis_hints, and benchmark results

## Context

The previous workspace refactoring (159) removed petgraph/composite storage and split nexus-model into nex-core, nex-fih, and nex-storage. This cleaned the dependency graph but did not change the underlying storage mechanics: every FIH query still performed a full scan across all facts, constructing `FactRecord` structs for each row, then filtering in memory.

The bottleneck was structural. The old `FihStorage` stored facts in a single `Vec<FactRecord>`. A filtered query (by creator, by origin, or any AND combination) iterated the entire vector. Even a single-field filter like "give me all facts by creator X" scanned all records, deserialized each into a `FactRecord`, checked the field, and either kept or discarded. The cost was dominated by Fact construction -- allocating `String`, `Vec<u8>`, `HashMap<String, String>` per row.

The theoretical ceiling for any filtered query under this model was approximately 28ms (the time to scan, construct, and drop 10K facts). Adding AND dimensions could not improve this, because the scan was already the full set.

synTagma's `CoordSpaceN<6>` offered a way out. Instead of storing heavyweight `FactRecord` values in a single linear array, we store lightweight `String` IDs in a 6-dimensional coordinate space. The HashMap remains as a complementary data store for the actual payloads, keyed by those IDs. This decouples index scanning from payload construction: a filtered query iterates the coordinate space (coordinates are small, fixed-size integers), collects matching IDs, and only then fetches the corresponding facts from the HashMap. If the index scan eliminates enough candidates, the HashMap lookups are cheap.

## Key decisions

### CoordSpaceN stores String IDs, not FactRecord payloads

This was the critical design insight. `CoordSpaceN<6>` stores an `Option<String>` at each coordinate -- just a fact ID (or `None` if the slot is vacant). The actual `FactRecord` (with its full content, metadata, and blobs) lives in a companion `HashMap<String, FactRecord>`.

The benefit is that index compaction, iteration, and prefix queries all operate on 8-byte coordinates + a small String handle. Fact construction only happens when the caller actually dereferences a match. If a query reduces 10K candidates to 10 matches, we construct exactly 10 `FactRecord` values instead of 10K.

```rust
// Conceptual layout (not production code)
struct CoordFihStorage {
    // 6D coordinate space: [time_hi, time_lo, entity, origin, creator, serial]
    space: CoordSpaceN<6>,
    // Complementary data store: ID -> FactRecord
    facts: HashMap<String, FactRecord>,
    // Fast-path single-field indices
    facts_by_creator: HashMap<String, Vec<String>>,
    facts_by_origin: HashMap<String, Vec<String>>,
}
```

### HashMap as complementary data store

The HashMap is deliberately simple -- no persistence, no disk sync, no ACID. It is the data store for the current in-memory epoch. On shutdown, facts are serialized to FileIo (parquet-backed). On restart, they are reloaded into the HashMap.

This design anticipates a future Chton backend that replaces the HashMap with a memory-mapped region (mmap). Chton would store fact payloads directly in a Coord-native binary format, eliminating the serialize/deserialize round-trip entirely. The HashMap is a placeholder that lets us validate the dual-storage architecture now, while keeping the migration path clear.

### facts_by_creator / facts_by_origin fast-path indices

Even with CoordSpaceN index scans, multi-dimensional prefix queries require iterating a subset of the space. For the most common single-field lookups -- "all facts by creator X" or "all facts by origin Y" -- we added dedicated `HashMap<String, Vec<String>>` indices.

These are write-amplified (each insert appends the fact ID to two vectors) but provide O(1) read: a single HashMap lookup returns every fact ID for that creator or origin, with no CoordSpaceN iteration at all. The cost is acceptable because write volume is low relative to read volume in the blackboard pattern (agents write facts at discrete intervals but read continuously).

The tradeoff is that these indices are maintained eagerly on every `insert_fact`. Deletions (`evict`) must also remove IDs from both vectors, which is O(n) in the number of facts for that creator/origin. For the current scale (10K facts per epoch), this is acceptable. If scale increases by 100x, we would need a secondary index structure (e.g., B-tree or suffix array) for O(log n) removal.

### axis_hints + query_prefix for CoordId-based iter_prefix queries

`CoordSpaceN` exposes `iter_prefix(prefix: &[Option<u64>])` which iterates all coordinates matching a given prefix pattern. However, callers work with `CoordId<6>` values (typed 6-element arrays), not raw prefix slices. Worse, the axis mapping is an internal convention -- the caller should not need to know that axis 0 is `time_hi` and axis 3 is `origin`.

`axis_hints` bridges this gap. An `AxisHints` struct maps semantic field names to axis positions and optionally provides a query builder:

```rust
struct AxisHints {
    axis_map: HashMap<String, usize>,  // "creator" -> 4, "origin" -> 3, etc.
}

impl AxisHints {
    /// Build a prefix for `iter_prefix` from a partial CoordId.
    /// Only the axes listed in `active` are used; the rest are `None`.
    fn query_prefix(&self, coord: &CoordId<6>, active: &[&str]) -> Vec<Option<u64>> {
        let mut prefix = vec![None; 6];
        for axis_name in active {
            if let Some(&axis) = self.axis_map.get(*axis_name) {
                prefix[axis] = Some(coord[axis]);
            }
        }
        prefix
    }
}
```

This lets callers write:

```rust
let prefix = hints.query_prefix(&coord, &["creator", "origin"]);
for match_id in space.iter_prefix(&prefix) {
    // ...
}
```

Without `axis_hints`, the caller would need to know that `coord[4]` is the creator and `coord[3]` is the origin, and manually construct `[None, None, None, Some(origin), Some(creator), None]`. This is error-prone and couples business logic to axis layout.

### AND query via HashSet intersection

Multi-dimensional AND queries (e.g., "facts by creator X AND origin Y") use a different strategy. Instead of iterating CoordSpaceN with a multi-axis prefix, we:

1. Look up `facts_by_creator["X"]` -> `Vec<String>` (O(1))
2. Look up `facts_by_origin["Y"]` -> `Vec<String>` (O(1))
3. Intersect the two vectors via HashSet: collect the smaller into a HashSet, iterate the larger, keep matches.

This avoids CoordSpaceN iteration entirely for AND queries. The cost is proportional to the size of the smaller set plus the intersection scan.

Benchmark results confirm the improvement:

| Query | OLD (ms) | NEW (ms) | Speedup |
|-------|----------|----------|---------|
| single-field (creator) | 27.8 | 0.074 | 376x |
| AND 2-dim (creator + origin) | 27.9 | 0.021 | 1315x |
| write 10K facts | 1776 | 1600 | 0.9x (slightly slower) |
| read_state (load 10K) | 13.2 | 11.0 | 1.2x (1.2x faster) |

The gap grows geometrically with AND dimensions because the OLD path does not improve with added filters -- it always scans all 10K facts. The NEW path benefits from HashSets that shrink the candidate set with each added dimension.

### Time range query regression: 6000x slower

There is one significant regression. Time range queries ("facts between T1 and T2") are 6000x slower in the NEW implementation. The reason is straightforward: there is no time index yet.

In the OLD implementation, time was just another field on `FactRecord`, so a time filter worked like any other field filter -- scan all, check the field. In the NEW implementation, time is split across two axes (`time_hi` and `time_lo`, axes 0 and 1), but `iter_prefix` does not support range iteration. A time range query falls back to scanning all coordinates, checking the time bounds manually, and then fetching matching facts -- the same O(N) cost as OLD plus the HashMap lookup overhead.

Fixing this requires either:
- A dedicated time-range index (e.g., a B-tree mapping `(time_hi, time_lo) -> Vec<String>`, analogous to `facts_by_creator`)
- An `iter_range` method on `CoordSpaceN` that iterates coordinates within a hyper-rectangle instead of a prefix

This is the next priority.

## Benchmark methodology

All benchmarks run on an Apple M3 Max (64 GB) with release profile (`cargo bench`). 10,039 facts pre-loaded into each storage backend. Queries are randomly generated from the fact distribution (10 distinct creators, 50 distinct origins). Each data point is the median of 10 runs.

OLD implementation: `Vec<FactRecord>` with linear scan + filter.
NEW implementation: `CoordSpaceN<6>` + `HashMap<String, FactRecord>` + fast-path indices.

## Known gaps

- `iter_prefix` on `CoordSpaceN` is not yet optimized for sparsely populated spaces. If a prefix matches few coordinates, the iteration is fast. If it matches many (e.g., a broad time range with no other filters), it approaches O(N) scan cost.
- `facts_by_creator` and `facts_by_origin` are eagerly maintained, which adds ~10% overhead to every `insert_fact`. For bulk-load scenarios (e.g., restoring a checkpoint), this overhead accumulates.
- The axis convention `[time_hi, time_lo, entity, origin, creator, serial]` is hardcoded in `CoordFihStorage`. Making it configurable would require generic axis mapping, which adds type complexity. For now, the convention is documented and enforced at the module boundary.
- Chton integration is not started. The HashMap backend is a stepping stone.
